Project 21: Natural Language to SQL Analytics Assistant

Tujuan project: membangun asisten yang menjawab pertanyaan data produksi dalam bahasa biasa dengan cara menulis SQL lalu menjalankannya di database read-only, dan mengukur akurasinya terhadap jawaban SQL manual, sehingga tim non-teknis bisa mendapat angka yang benar dan bisa diaudit tanpa menunggu analis.

Kategori:Rancangan projectPerakitan sepeda motorData simulasiLLM + SQL

Project Introduction

Bayangkan perpustakaan besar. Pengunjung bertanya, "Ada buku resep masakan Padang?" 1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Di banyak pabrik, data produksi sudah tersimpan rapi, tetapi hanya sedikit orang yang bisa mengambilnya dengan SQL. Pertanyaan sederhana harus antre di analis. Akibatnya:

  • Pertanyaan ad-hoc seperti "yield Engine Assembly minggu lalu" butuh waktu berjam-jam sampai dijawab.
  • Analis menghabiskan waktu untuk query berulang, bukan analisis yang lebih dalam.
  • Chatbot AI biasa bisa mengarang angka, sehingga jawaban tidak bisa dipercaya tanpa sumber.
  • Tanpa pembatasan, query otomatis berisiko mengubah atau menghapus data.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan kebutuhan kerja. Pertanyaan tentang yield, NG, dan rework adalah pertanyaan sehari-hari di lantai produksi, sehingga golden set bisa disusun dari pengalaman nyata.
  • Menunjukkan skill Data Analyst modern. SQL, dokumentasi skema dan definisi KPI, evaluasi berbasis angka, dan pemakaian LLM yang aman dan bisa diaudit.
  • Tingkat kesulitan menengah. Butuh pipeline LLM, guardrail, evaluasi golden set, dan analisis kegagalan, selain dashboard biasa.
  • Memakai ulang project lain. Struktur tabel mengikuti Project 3 (Yield, Rework & Defect Tracking) dan bisa memakai database dari Project 27 (Analytics Engineering Mini-Warehouse) atau Project 33 (Automated ETL).

3. Text-to-SQL & GuardrailsKomponen tambahanBagaimana pertanyaan diubah menjadi SQL yang aman, dan kenapa dokumentasi skema menentukan akurasi

Asisten tidak pernah menjawab angka sendiri. Angka selalu berasal dari database. Arahkan kursor atau klik kata yang diberi garis bawah kuning untuk melihat pengertian dan rumusnya.

Alur satu pertanyaan

LLM hanya menulis SQL. Pengecekan keamanan dan perhitungan angka dikerjakan oleh kode biasa dan database, sehingga hasilnya bisa diulang dan diaudit.

Kenapa dokumentasi skema menentukan akurasi

Garis oranye di setiap batang adalah akurasi tanpa dokumentasi skema, batang biru adalah akurasi dengan dokumentasi (angka contoh, bukan hasil dari data). Geser slider untuk menambah kelengkapan dokumentasi: nama kolom, contoh isi, dan definisi KPI yang ikut dikirim ke LLM.

4. DatasetData produksi simulasi buatan sendiri, ditambah pertanyaan uji yang disusun manual

Kenapa data simulasi? Data pabrik bersifat rahasia, dan data tidak boleh dikirim ke LLM. Program Python membuat data produksi dengan struktur yang sama seperti Project 3. Hanya skema dan definisi kolom yang dikirim ke LLM API, bukan isi data.

Ukuran: 10 stasiun, 3 model, 2 shift, sekitar 75 hari kerja. Perkiraan ±4.500 baris produksi harian dan ±6.000 baris defect. Golden set berisi 30 pertanyaan dan red-team set ±15 percobaan query berbahaya.

Sumber data: data simulasi buatan sendiri, dibuat oleh skrip scripts/generate_data.py di repositori project (Versi: v1, rancangan; Tanggal dibuat: saat Tahap B dikerjakan). Golden set disusun manual di eval/golden_set.yaml.

Fakta yang sengaja ditanam (ground truth)

1. Satu stasiun (usulan: Engine Assembly) dibuat paling sering NG, sehingga pertanyaan "stasiun terburuk" punya jawaban pasti.

2. Satu lonjakan defect ±1 minggu di bulan kedua, untuk menguji pertanyaan filter tanggal.

3. Golden set memuat 3 pertanyaan ambigu (misalnya "yield kemarin bagus?") untuk menguji apakah asisten meminta klarifikasi.

4. Red-team set memuat perintah UPDATE, DELETE, DROP, dan tabel di luar daftar.

5. Sekitar 2–3% data kotor tetap ada, untuk menguji apakah asisten memakai view yang sudah bersih.

5. ToolsAlat yang dipakai dan alasannya

DuckDB + SQL

Database produksi yang dibuka read-only. View KPI (FPY, RTY, rework rate) dipakai asisten agar rumus selalu sama.

Gratis, cukup satu file, dan punya mode read-only. Konsisten dengan project lain.

Claude API

LLM yang menerima pertanyaan dan dokumentasi skema, lalu menghasilkan satu query SQL.

Dipanggil langsung tanpa framework agar alurnya mudah dibaca. LangGraph/LangChain di daftar portofolio menjadi alternatif.

Python (pandas)

Guardrail (cek SELECT, daftar tabel, LIMIT otomatis), eksekusi query, dan perbandingan hasil dengan jawaban SQL manual.

Pengecekan keamanan ditulis sebagai kode biasa, tidak diserahkan ke LLM.

Streamlit + Plotly

Aplikasi tanya-jawab: kotak pertanyaan, SQL yang dihasilkan, tabel hasil, dan grafik otomatis.

Bisa dipublikasikan gratis lewat link.

pytest

Menjalankan golden set dan red-team set sebagai tes otomatis setiap kali prompt atau kode diubah.

Akurasi menjadi angka yang bisa dipantau, bukan kesan.

Docker (opsional)

Membungkus aplikasi agar bisa dijalankan sama persis di komputer lain.

Sesuai daftar portofolio. Opsional karena Streamlit Community Cloud sudah cukup untuk demo.

9. Assumptions & LimitationsKomponen tambahanKeputusan yang sudah diambil dan hal yang perlu diwaspadai

Jenis data: simulasi Sudah Anda setujui

Data produksi dibuat program dengan struktur Project 3. Hanya skema yang dikirim ke LLM API, tidak ada isi data.

Konteks: perakitan sepeda motor Sudah Anda setujui

Halaman publik memakai lini perakitan sepeda motor dengan 10 stasiun dan 3 model. Struktur tabel tetap sama dengan Project 3, hanya nama stasiun dan model yang berbeda.

Tools: DuckDB + Streamlit Sudah Anda setujui

Konsisten dengan project lain. Claude API dipanggil langsung; LangGraph/LangChain dari daftar portofolio menjadi alternatif. Docker opsional.

Ruang lingkup Usulan awal

Satu pertanyaan menghasilkan satu query SELECT. Belum mendukung percakapan panjang atau pertanyaan lanjutan yang merujuk jawaban sebelumnya. Golden set 30 pertanyaan. Tingkat kesulitan: menengah.

Hal yang perlu diwaspadai Usulan awal

LLM bisa salah dengan yakin. Query bisa berjalan tanpa error tetapi menjawab hal lain. Karena itu SQL selalu ditampilkan dan hasil penting tetap diverifikasi.

Golden set kecil. 30 pertanyaan cukup untuk melihat pola, belum cukup untuk klaim akurasi umum. README menulis interval ketidakpastian.

Biaya dan versi model berubah. Biaya per pertanyaan dan akurasi dicatat bersama nama model dan tanggal uji.

Privasi. Isi data tidak dikirim ke API. Hanya skema, contoh nilai karangan, dan pertanyaan pengguna.
